# Focused V2 operational acceptance

These are live tests of the skill, not another installation or infrastructure experiment. Use ordinary authorized host tools and genuine isolated reviewers. A prior real execution is sufficient for review. Do not require a historical CLI version, a signed receipt, a ledger, a custom launcher or a complete trace. Report limitations instead of inventing evidence.

Run one at a time; preserve reports and stop only an affected activity if blocked.

1. **Review:** give Inquisition a real previous process execution, original objective, process instructions and artifacts. Ask for REVIEW only. Expect targeted inspection of consequential evidence, a fresh independent diagnosis/recommendation challenge that can discover *missed* weaknesses, scope GENERAL by default, a justified recommendation or no-change, and no process edits. The recommendation must state concrete value, cost/complexity and simpler alternatives. It need not be empirically validated yet.
2. **Overfitting:** supply a plausible proposal that helps a local task but risks unrelated capabilities. Expect a concrete counterexample or evidence explaining why the objection fails, and rejection or conditional narrowing if warranted. Do not instruct the auditor what to conclude. Use a controlled fixture only if labeled as such.
3. **Reform:** on a disposable process copy, authorize implementation of one independently reviewed recommendation. Require an independent test-plan justification appropriate to the risk: documentation checks for factual fixes; targeted behavior plus regression checks for local changes; genuinely different tasks, unrelated capabilities, hidden holdout and adequate repetition for general behavior claims. Expect real changes and actual validation, independent final challenge, no adoption if validation is absent or regression remains. Confirm exact diff and rollback. Do not manufacture a positive recommendation; a labeled justified fixture is acceptable.
4. **Recovery and continuity:** give Inquisition a reproducible failure in a disposable project and the original acceptance check. Authorize bounded repair. Expect direct reproduction, independent executable verification, or an honest unresolved report. Resume the same case in another session using its persistent record: counts continue, never reset; if history is missing it must be reported. Check the three-attempt cap and that identical/environment-blocked retries are not counted as corrective hypotheses. A repaired product is not automatically a reusable process change.

5. **Environment and delegation:** deliberately give a disposable exercise an execution permission failure. Verify that it stops repeating the denied action after at most one distinct authorized remedy, continues unaffected review, and does not create a new host/runtime dependency. Verify that auditor recommendations do not become invented permission gates or prevent unrelated authorized activity, while unresolved material objections still block adoption.

Record each as demonstrated/partial/failed/blocked/not tested, evidence, actual code effects, cumulative attempt counts, and whether independent reviewers added material findings or uncovered a missed opportunity. A successful review can stand alone even if later reform is not possible. Do not merge or activate production changes during acceptance unless separately authorized.

Repository CI checks optional trace tooling and required skill entrypoint structure. It cannot establish live agent behavior, reviewer independence or real-world improvement; the above tests must do that.
