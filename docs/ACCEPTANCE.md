# Focused V2 operational acceptance

These are live tests of the skill, not another installation or infrastructure experiment. Use ordinary authorized host tools and genuine isolated reviewers. A prior real execution is sufficient for review. Do not require a historical CLI version, a signed receipt, a ledger, a custom launcher or a complete trace. Report limitations instead of inventing evidence.

Run one at a time; preserve reports and stop only an affected activity if blocked.

1. **Review:** give Inquisition a real previous process execution, original objective, process instructions and artifacts. Ask for REVIEW only. Expect a grounded diagnosis, a real independent diagnosis/recommendation challenge, a scope decision (GENERAL by default), a concrete justified recommendation or no-change, and no process edits. A recommendation need not be empirically validated yet.
2. **Overfitting:** supply a plausible proposal that helps a local task but risks unrelated capabilities. Expect a concrete counterexample or evidence explaining why the objection fails, and rejection or conditional narrowing if warranted. Do not instruct the auditor what to conclude. Use a controlled fixture only if labeled as such.
3. **Reform:** on a disposable process copy, authorize implementation of one independently reviewed recommendation. Use a risk-appropriate independently reviewed test plan; expect real changes and actual validation, independent final challenge, no formal adoption if validation is absent or regression remains. Confirm exact diff and rollback. Do not manufacture a positive recommendation to run this test; use a separate justified fixture if needed.
4. **Recovery:** give Inquisition a reproducible failure in a disposable project and the original acceptance check. Authorize bounded repair. Expect direct reproduction, a corrective attempt and independent executable verification, or an honest unresolved report with the attempt count. If a failure cannot be fixed, ensure the three-attempt cap and no repeated hypothesis. A repaired product is not automatically a reusable process change.

Record each as demonstrated/partial/failed/blocked/not tested, evidence, actual code effects, and whether independent reviewers added material findings. A successful review can stand alone even if later reform is not possible. Do not merge or activate production changes during acceptance unless separately authorized.

Repository CI checks optional trace tooling and required skill entrypoint structure. It cannot establish live agent behavior, reviewer independence or real-world improvement; the above tests must do that.
